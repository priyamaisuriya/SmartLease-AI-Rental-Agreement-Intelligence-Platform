# 2. CORE SMARTLEASE RENTAL FLOW

The main rental workflow must become:

```text
Landlord registers/logs in
        ↓
Landlord adds property
        ↓
Landlord defines property information
        ↓
Landlord defines rental conditions / common agreements
        ↓
Property becomes available for tenants
        ↓
Tenant searches property
        ↓
Tenant opens property details
        ↓
Tenant reads property conditions
        ↓
Tenant can use AI to understand/analyze conditions
        ↓
Tenant selects rental start date + end date
        ↓
System validates dates
        ↓
Tenant submits rental request
        ↓
Landlord receives notification
        ↓
Landlord reviews request
        ↓
Landlord ACCEPTS or REJECTS
        ↓
If REJECTED
    → Tenant is notified
    → Tenant can choose dates again
    → Tenant can submit another request
        ↓
If ACCEPTED
        ↓
Landlord uploads/generates rental agreement
        ↓
Tenant receives agreement notification
        ↓
Tenant views/downloads agreement
        ↓
AI Agreement Analysis available
        ↓
Tenant ACCEPTS agreement
        ↓
Payment becomes available
        ↓
Tenant makes payment
        ↓
Payment succeeds
        ↓
Booking confirmation becomes available
        ↓
Tenant confirms booking
        ↓
Rental/Booking becomes CONFIRMED
        ↓
Property is unavailable for overlapping dates
        ↓
Invoice becomes available
```

This must be implemented as a proper state-based workflow.

# 6. PROPERTY SEARCH

IMPORTANT:

**DO NOT REMOVE PROPERTIES FROM SEARCH merely because they currently have a confirmed booking.**

Search should continue showing properties that may be available for other dates.

For example:

Property A:

```text
Booked:
01/11/2026 → 30/11/2026
```

A tenant searching:

```text
15/11/2026 → 20/11/2026
```

must not be allowed to request it.

But a tenant searching:

```text
01/12/2026 → 15/12/2026
```

should still be able to see and request it.

Therefore:

### Search visibility ≠ booking availability

Always keep properties visible unless the property itself is inactive/deleted/unlisted according to existing business rules.

Availability must be determined based on requested dates.

# 7. RENTAL DATE VALIDATION

Implement strong date validation on BOTH:

### Client side

AND

### Server side

Never rely only on frontend validation.

Rules:

### Start date

The rental start date:

* Cannot be in the past.
* Cannot be today if the business rule requires bookings to begin from the next valid rental day.
* Must satisfy the project's minimum advance-booking rule.
* Must be a valid date.
* Must be before the end date.

```text
10 October
```

```text
09 October
```

or any earlier date.

Implement the exact minimum start-date rule consistently across frontend and backend.

# 8. END DATE VALIDATION

End date:

* Must be valid.
* Must be after start date.
* Cannot be before start date.
* Must satisfy minimum rental duration.
* Must satisfy maximum rental duration if configured.
* Must not create an invalid rental period.

Use consistent date handling.

Avoid timezone-related off-by-one-day bugs.

Normalize dates appropriately on the backend.

# 9. BOOKED DATE VALIDATION

A tenant must NOT be allowed to request dates that overlap with an already confirmed booking.

Use proper date-overlap logic.

Two rental periods overlap when:

```text
requestedStart < existingEnd
AND
requestedEnd > existingStart
```

Use the same business rule consistently across:

* Search
* Property details
* Rental request API
* Booking API
* Payment/confirmation
* Backend validation
* Admin actions

Do not rely only on checking whether dates are exactly equal.

Example:

Existing booking:

```text
10 Nov → 20 Nov
```

The following must be rejected:

```text
5 Nov → 12 Nov
15 Nov → 25 Nov
10 Nov → 20 Nov
12 Nov → 18 Nov
1 Nov → 30 Nov
```

A non-overlapping period should remain requestable according to the application's boundary-date policy.

# 10. MULTIPLE TENANT REQUESTS

Multiple tenants can request the same property for the same dates while the requests are still pending.

Example:

```text
Tenant A → 1 Dec to 31 Dec → PENDING
Tenant B → 1 Dec to 31 Dec → PENDING
Tenant C → 1 Dec to 31 Dec → PENDING
```

This is allowed.

The property should continue appearing to other tenants.

However, once one request becomes the confirmed booking for those dates:

```text
Tenant A → CONFIRMED
```

the system must prevent the other overlapping requests from being accepted/confirmed.

---

# 11. IMPORTANT CONCURRENCY RULE

This is a critical backend requirement.

Suppose:

```text
Tenant A request → 1 Dec–31 Dec
Tenant B request → 1 Dec–31 Dec
```

Both are pending.

Landlord/admin must NOT be able to accept both.

When the first request becomes accepted/confirmed:

```text
Tenant A → CONFIRMED
```

then Tenant B's overlapping request must become unavailable for acceptance.

The backend must re-check date availability immediately before accepting/confirming.

Do NOT rely on the state displayed earlier in the UI.

Prevent race conditions as much as reasonably possible using:

* Backend revalidation
* Atomic/transactional operations where appropriate
* Database constraints/indexing where practical
* Status checks
* Date-overlap checks immediately before confirmation

The server must be the final authority.

# 48. IMPORTANT BUSINESS RULE

The property is an entity.

The booking is date-specific.

Therefore:

```text
Property ≠ permanently booked
```

Instead:

```text
Property
    ├── Booking: 01 Jan → 31 Jan
    ├── Booking: 01 Mar → 31 Mar
    └── Available: other valid dates
```

This concept must be reflected throughout the application.

AI must enhance SmartLease, not replace core business rules.

AI can:

* Explain conditions
* Analyze agreements
* Summarize documents
* Answer document questions
* Highlight important clauses

AI must NOT decide:

* Whether dates are available
* Whether booking is valid
* Whether payment succeeded
* Whether user has permission
* Whether landlord accepted request
* Whether booking is confirmed

Those decisions must come from deterministic backend business logic.
